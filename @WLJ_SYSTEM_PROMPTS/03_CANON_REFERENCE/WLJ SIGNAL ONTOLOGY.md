WLJ SIGNAL ONTOLOGY

Version: 1.1
Last updated: 2026-05-04

Signals are the canonical interpretation layer between raw data and the CoS.

All domains should emit signals that conform to this model.

---

CANONICAL SHAPE — UnifiedSignal

Producers emit signals in their domain-native form. The unified feed (apps/core/ai_signals/unified_feed.py) consolidates them into a single shape:

domain          str    health, medical, faith, life, meals, ...
type            str    canonical type (e.g., glucose_high, faith_streak)
severity        str    alert | warning | info
priority_tier   str    foundational | important | supporting
confidence      float  0–1
dedupe_key      str    used for cluster collapse across producers
source          str    guidance | insight | prediction | cross_domain | correlation | drift
evidence        list   structured pointers to records that justify the signal
explain_why     str    deterministic, system-generated; not LLM prose
recency         dt     when the underlying observation occurred

Required fields: domain, type, severity, confidence, dedupe_key, source.
Missing required fields → the signal is dropped.

---

PRODUCERS

PIE — Proactive Insight Engine
   Detects single-domain factual patterns via registered rules.

PRIE — Predictive Intelligence Engine
   Linear-regression trajectory + confidence; future-tense signals.

PGE — Proactive Guidance Engine
   Evidence-based recommendations; reads SAE + PIE + PRIE.

CDCE — Cross-Domain Correlation Engine
   Statistical relationships across domains (e.g., "sleep < 6.5h → negative mood 78%"). Runs on a 6-hour cadence.

Drift — direct ORM-read telemetry that flags when CoS reads bypass SAE; tracked as a signal source so it surfaces in dashboards.

---

PRIORITY TIERS

foundational — health, medical (life-impact)
important    — meals, nutrition, sleep, habits, faith
supporting   — life, tasks, routine, organization, notes

select_top_signals sorts by (priority_tier, severity, confidence, recency); foundational signals always surface.

---

SOURCE PRECEDENCE

When two producers emit overlapping signals, the source order is:

1. Guidance (PGE)
2. Insight (PIE)
3. Prediction (PRIE)
4. Cross-domain (CDCE)
5. Correlation
6. Drift

Higher-precedence signals override lower-precedence ones during dedupe-key collapse.

---

FOUNDATIONAL SUPPRESSION (CONFLICT RESOLUTION)

resolve_conflicts drops same-domain non-foundational signals when a foundational signal exists in the same domain.

Example: glucose_high (foundational) suppresses weight_loss_positive (non-foundational) for the same window.

---

LABEL TAXONOMY

The renderer accepts exactly three labels:

Alert        — immediate attention required
Trend        — directional change worth noting
Opportunity  — actionable improvement available

Forbidden labels: Unclear, Mixed, Needs clarity. These produce no actionable user behavior and are rejected.

---

RENDERER (TABLE-DRIVEN, NO LLM)

apps/core/signals/signal_renderer.py is the single canonical interpretation layer.

SIGNAL_RENDER_MAP[(domain, type, severity)] → template

The renderer:

• Computes label, message, action deterministically from the template.
• Does NOT read signal.title or signal.message — normalize_signal strips them so producer prose cannot leak through.
• Has zero LLM calls in its execution path.

LLM rephrasing of rendered output is allowed; LLM construction of factual statements is forbidden.

_TYPE_ALIAS is a temporary translation layer mapping producer types to canonical renderer types. Phase 2 retires the alias by migrating producers to emit canonical types directly.

SIGNAL TYPES

1. Event Signals

Something occurred.

Examples:

workout_completed  
meal_logged  
journal_entry_created  
sermon_listened  
meeting_recorded

---

2. Metric Signals

A measurable state or trend exists.

Examples:

sleep_deficit  
glucose_variability_high  
goal_momentum_declining  
weekly_training_load_high

---

3. Pattern Signals

A meaningful relationship exists across time or domains.

Examples:

travel_disrupts_routine  
poor_sleep_precedes_glucose_spikes  
exercise_improves_mood

---

4. Influence Signals

Content or learning influences behavior.

Examples:

discipline_theme_detected  
leadership_theme_detected  
marriage_growth_theme  
faith_learning_event

Often generated by Capture.

---

5. Intent Signals

Potential actions inferred from learning or planning.

Examples:

relationship_action_suggested  
spiritual_growth_prompt  
habit_change_intent

---

TIME HORIZONS

Signals should support multiple time windows.

short-term: hours / days  
medium-term: weeks  
long-term: months  
historical: lifetime

The CoS must be able to reason across these windows.

DECISION-LAYER CONSUMPTION (CoS Modes + Recovery Contract)

Signals feed three deterministic CoS decision modes (Execution, Risk, Fix). The decision pipeline composes:

Today Engine (build_today_execution)
  → Execution State (build_execution_state)
    → Action Prioritizer (recoverability + collapse + at-risk + recovery-mode bucketing)
      → Selectors (pure picks; no priority computation)

Recovery contract artifacts that influence which signals reach the user:

• task_class ∈ {HARD_EXPIRED, WINDOWED, SOFT_EXPIRED, FLEXIBLE}
• is_recoverable(item, now)  — WINDOWED hard cutoff at next anchor block
• is_reset_action            — derived from activity_type / domain / registry; never from titles
• RecoveryState.mode ∈ {NORMAL, RECOVERY, STABILIZE, SHUTDOWN}
• RecoveryState.day_narrative ∈ {on_track, behind_recoverable, behind_reset_required, day_lost_salvage, evening_closeout}
• BlockCollapse.strategy ∈ {recover_partially, skip, defer}
• at_risk_actions: 60–90 min standard horizon; 4 h with dependency chain only; suppressed when overdue exists and no dependency

These layers run upstream of selectors. Selectors must remain pure picks.
